# Broker fleet synchronization

The Broker is the registration authority. A read-only, repeatable-read transaction publishes a complete roster every 30 seconds. Nodes require an enabled resource and account, no retirement, Kubernetes runtime type, and provider state RUNNING. Windows require those activation conditions plus an enabled Windows connection. Missing node UID or credentials stays visible as unverified; it is never inferred from another node. A disabled or retired resource, a removed registration, or a stopped provider instance leaves the active roster.

SLA keeps static service probes and adds individual node and Windows targets from that roster. IDs derive from resource_target_id and survive name changes. The dashboard keeps its five service groups, including each Windows listener as its own asset. No per-fleet count or per-node credential is written to the profile when membership changes.

POST /ingest/fleet/roster accepts only the publisher credential. GET /ingest/fleet/desired and POST /ingest/fleet/observations accept only the observer credential. These keys cannot access admin APIs or report to static targets. Membership and observation contracts are versioned in the adjacent JSON schemas. The aggregate member limit is 64, and request bodies are limited to 256 KiB. Partial, duplicate, out-of-order and invalid snapshots do not replace the last accepted roster. Atomic storage restores registration after a restart; health requires fresh observation after restart.

The Runtime observer obtains existing Broker credentials per node, validates the resource UUID, Node UID, endpoint, embedded CA, client certificate fingerprint and expiry, and runs GET-only kubectl queries. Exec plugins, proxy URLs, insecure TLS and external credential files are rejected. Temporary kubeconfigs are mode 0600 under the service RuntimeDirectory and removed after each query. Windows checks only connect to the registered RDP TCP listener and send no application payload. It does not open RDP sessions or request execution, recovery or reservations.

A membership version binds every complete observation batch to the accepted roster. A delayed batch for removed or rebuilt members is rejected. Missing source updates retain the last known registrations but mark them unverified after 180 seconds. Observation age is independent: roster heartbeats do not extend old health readings. Registration normally appears on the next publisher and dashboard refresh; actual health appears after the next observer cycle, typically within one to two minutes.

The Broker publisher runs a fixed SELECT-only Python command in the existing Broker container and exports only the allowlisted registration fields. It never exports account credentials, RDP profiles, usernames or kubeconfigs. The observer loads the existing Runtime Broker token through systemd LoadCredential on every execution, so token rotation does not require copying it into another configuration file.

Deploy the fixed broker-fleet status target and two role-separated keys once, start the publisher and observer units, and remove the superseded manual worker-node and Windows bindings after accepted fresh reports. Preserve the local Runtime node collector. Existing service probes, risk thresholds, event history and challenge ownership boundaries remain independent of discovery.

## Runtime collector deployment

Production builds from dev set runtime_telemetry in the existing release manifest. The EC2 deployment uses the existing runtime operations binding and its source-restricted sentinel-ops key to invoke the fixed telemetry-deploy command. The SSH host key must match the configured SHA-256 pin before any authentication. A temporary mode-0600 key file is removed on success, remote error or timeout. No additional GitHub secret, cloud role, inbound rule or participant operation is required.

Runtime installs runtime_deploy.py once as root-owned /usr/local/libexec/sentinel-telemetry-deploy and permits that command without arguments in the existing sentinel-ops sudoers rule. The forced SSH entry accepts only the complete telemetry-deploy literal; the dashboard action API remains status, resources and start. Preserve the existing authorized_keys source restriction and key. The installer accepts only revision, run_id and run_attempt, verifies the current dev commit and the successful verify job of that exact production workflow attempt, and fetches its fixed file manifest from this public repository. Pull requests, stale commits, other workflows and failed or incomplete verification are rejected.

runtime-release.json records each collector, unit and installer digest and the official Linux amd64 kubectl v1.36.5 URL and SHA-256. Every deployment downloads and verifies that client before atomic installation. The client and all its parent directories must be root managed and not group or world writable. Hosts without that dedicated client keep their existing kubectl path. Node inventory uses GET /api/v1/nodes without discovery; the Node UID, embedded TLS material, certificate fingerprint, expiry and metrics identity guards remain required.

Collector files are atomically replaced without stopping application services, timers or workloads. Existing module interfaces must remain compatible while a running observer finishes. Installation keeps CPUQuota=30%, waits for a new accepted periodic observation and checks that the Runtime application processes and registry remain unchanged. A failed installation restores the previous sources and client. The root-owned deployment receipt records the GitHub revision and attempt, file and client hashes, effective quota and fresh native acceptance; it is also checked by the EC2 deployment before that deployment can succeed. A later full redeployment repeats this process rather than depending on a manual server patch.

Regenerate the file hashes in runtime-release.json when changing a managed file; the telemetry test suite verifies those hashes against repository contents. Changing kubectl requires updating both its official pin and the reviewed executable selector. The installer updates its own fixed executable from the approved commit, so normal future deploys retain the same deployment path.
